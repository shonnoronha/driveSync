# ADR 0008: The app's screens (step 6)

Date: 2026-11-13 · Status: proposed (please review)

## Shape
- Every screen is split into three pieces:
  - a **stateless composable** that takes a UI state and an actions object;
  - a **thin ViewModel** (Hilt) that maps repositories into that state;
  - a **route** that connects the ViewModel to system pickers and permission prompts.
- State mapping that holds logic is written as plain Kotlin functions with JVM unit tests: `homeState`,
  `AddPairRules`, `activityDays`, `conflictsState`.
- **Screenshots:** Roborazzi with Robolectric native graphics renders every screen to `app/screenshots/` on the
  JVM, on a Pixel-sized screen, using the static theme so images are stable. `./gradlew :app:recordRoborazziDebug`
  updates them; `verifyRoborazziDebug` can later guard against unintended UI changes in CI.
- **Module placement:**
  - `feature-pairs`: home, add-folder wizard and pair detail.
  - `feature-settings`: onboarding and settings.
  - `feature-activity`: the log, plus the activity row that pair detail reuses (`feature-pairs` depends on it).
  - `feature-conflicts`: the conflicts screen.
  - `app`: the `NavHost`, theme and start destination.

## Decisions
1. **Start destination:** onboarding until an account is stored, then home. Opening the app starts a catch-up
   sync (PRD 3.4 item 12).
2. **Sync progress:** home shows a thin progress bar, and a "Syncing" chip on the pair being synced. One-pair
   runs are tagged with the pair id; an all-pairs run marks every enabled pair.
3. **Add folder:**
   - It blocks folders that overlap an existing pair: the same folder, a parent or a child (FR-P7).
   - It warns, without blocking, about non-device storage and when 100 folder grants are in use (PRD 6.2).
   - Linking an existing Drive Sync folder reuses that folder's pair id, so the same pair has one id on every
     phone (PRD 3.10).
   - The review step counts files on both sides. It does not run the planner; it says plainly that the first
     sync only copies and links.
4. **Per-file conflict answers:** these needed an engine change (`PlanInput.resolutions`, a path → policy
   override).
   - Answers are stored until the pair's next completed run, which applies and then clears them.
   - Choosing an answer starts a sync of that pair.
   - Modify/delete conflicts offer only "Keep the file", because the planner always keeps the modified version.
   - File-vs-folder clashes and duplicates on Drive explain what to do; they offer no buttons.
5. **Fixes from pair detail:**
   - **Try again.**
   - **Choose the phone folder again:** drops the base, so the next run only merges.
   - **Recreate the Drive folder:** relinks the pair, which also drops the base.
   - **Confirm deletes.**
   - **Restore instead of deleting:** drops the base, so the missing files are copied back.
   - **Remove:** never touches phone files. The Drive folder goes to the trash only if you tick the box
     (PRD 3.8).
6. **Sign-out (FR-A5),** in order:
   1. Cancel all background work.
   2. Release the folder grants.
   3. Revoke Drive access (best effort when offline).
   4. Clear the database and settings.

   Your files stay put.
7. **Settings added:** theme (system, light or dark) and dynamic color. The predictive back gesture is enabled
   in the manifest.
8. **"Sync now"** ignores the Wi-Fi-only and charging-only rules (ADR 0007). The settings text says so.

## Not done yet
- **Tablets and foldables** (list-detail, navigation rail) still use the phone layout.
- **Conflicts screen:** no side-by-side size, date and device metadata (PRD 8.5), because conflicts store only
  the path and the outcome.
- **Source and issue links** point at a placeholder URL until the repository is published.
- **Quick Settings tile, widget and a licenses screen** are not built.
- **Nothing has run on a device yet.** Sign-in, the folder picker, permissions and navigation are verified only
  by compiling and by screenshots of the stateless screens. Step 7 covers the device.
